## Authority and specialization

Each page owns a distinct subject; use links for related standards rather than repeating rules.
Read requirements in their stated scope. A language-specific convention or a real-time constraint
is not automatically a universal engineering rule. Explicit project contracts provide concrete
bindings and documented specializations; an unresolved material conflict requires clarification,
not an assumption that the newest or most local prose must be correct.

These are normative working standards, not empirical claims that one technique is optimal for all
systems. Justify departures with the affected rule, consequences and the applicable approval.
No guideline or skill grants edit, release or external-action permission. Consult the
[project layout](../docs/README.md#project-layout) for the four project spaces and their
responsibilities. Project documentation owns local conventions and decisions.
